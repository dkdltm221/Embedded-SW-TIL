# 무기체계 SW 개발 프로세스 및 관리

2026-11-25

## 방산 소프트웨어 개발의 특징

무기체계에는 여러 부체계와 구성품이 포함된다. 내장형 SW를 개발할 때는 담당 소프트웨어의 기능과 함께 타깃 하드웨어, 실행 환경, 다른 구성품과의 인터페이스를 파악해야 한다.

개발 초기에 사업에 적용되는 규정과 개발·관리 매뉴얼을 바탕으로 절차, 역할, 산출물, 검토 기준을 정한다. 요구사항과 설계 문서, 사용 매뉴얼, 시험 계획·절차·결과를 관리한다. 여러 조직이 참여하는 사업에서는 요구사항 변경이 다른 구성품이나 시험에 미치는 영향도 함께 확인한다.

소프트웨어는 내부 구조가 겉으로 드러나지 않고 구성요소 간 관계가 복잡하다. 사용 환경과 요구사항에 맞춰 지속적으로 개선할 수 있으며, 가능한 입력과 실행 환경을 모두 시험하기는 어렵다. 공통 문서와 검토 기준은 이해관계자 간 해석 차이와 개발 경험에 따른 편차를 줄이는 데 도움이 된다.

### 소프트웨어 유형과 구성 단위

| 유형 | 의미 | 도입·개발 시 확인할 사항 |
| --- | --- | --- |
| COTS | 상용 기성 소프트웨어(Commercial Off-The-Shelf) | 기존 제품으로 개발 범위를 줄일 수 있는지, 등록·승인 절차가 필요한지 확인한다. |
| GOTS | 정부용 기성 소프트웨어(Government Off-The-Shelf) | 사업에서 사용할 수 있는 범위와 조건을 확인한다. |
| 개발 SW | 사업 요구사항을 충족하도록 개발하는 소프트웨어 | 사업 요구사항과 설계·구현·시험 결과를 연결해 관리한다. |
| OSS | 오픈소스 소프트웨어(Open Source Software) | 라이선스별 배포·소스 공개 의무와 사업의 보안 및 지식재산권 조건을 확인한다. |

| 계층 | 영문 명칭 | 역할 |
| --- | --- | --- |
| CSCI | Computer Software Configuration Item | 소프트웨어 형상항목. 독립적으로 식별하고 변경을 통제하는 단위다. |
| CSC | Computer Software Component | 소프트웨어 구성품. CSCI를 구성하며 CSU로 세분화할 수 있다. |
| CSU | Computer Software Unit | 단위 소프트웨어. 설계에서 식별하는 최소 단위다. |

CSCI의 경계는 기능, 규모, 복잡도, 독립적인 변경 통제와 문서화 필요성을 고려해 정한다. 유사 사업의 구성과 산출물도 참고할 수 있다.

## 개발 모델

| 모델 | 진행 방식 | 관리 관점 |
| --- | --- | --- |
| 폭포수 모델(Waterfall Model) | 요구사항 분석 → 설계 → 구현 → 시험 → 유지보수 | 단계마다 산출물을 작성하고 검토한다. 후반부 요구사항 변경은 앞 단계의 산출물에 영향을 줄 수 있다. |
| V 모델(V-Model) | 분석과 설계를 구체화한 뒤 구현하고, 단위에서 체계로 시험 범위를 넓힌다. | 분석·설계 단계에서 대응하는 시험을 계획하고 요구사항과 시험 결과의 추적 관계를 관리한다. |

강의에서는 LIG의 개발 사례로 V 모델을 소개했다. 다음은 개발 활동과 시험 활동의 대응 관계를 보여 주는 예시다.

| 개발 활동 | 대응하는 시험 활동 | 확인 대상 |
| --- | --- | --- |
| 체계 요구사항 분석 | 체계 시험 | 통합된 체계가 상위 요구사항을 충족하는지 확인한다. |
| SW 요구사항 분석 | SW 요구사항 검증 시험 | 소프트웨어가 SRS에 정의된 기능과 품질 기준을 충족하는지 확인한다. |
| SW 구조 설계 | SW 통합시험 | 구성요소 사이의 인터페이스와 연동 동작을 확인한다. |
| SW 상세설계 | SW 단위시험 | 개별 소프트웨어 단위의 동작을 확인한다. |

## 체계개발 단계와 산출물

발주기관이 제안요청서(RFP)를 발행한다. 사업 수주 후 개발 계획을 수립하고, 체계 요구사항에서 SW 요구사항을 도출해 설계·구현·시험을 진행한다.

| 개발 단계 | 주요 업무 | 주요 산출물 | 관련 기술 검토 |
| --- | --- | --- | --- |
| 체계 요구사항 분석 | 운용개념을 수립하고 체계 요구사항과 주요 구성품을 식별한다. | SSS, SSRS | SRR(체계 요구사항 검토) |
| 체계 구조 설계 | 체계 기능을 구성요소에 할당하고 내부·외부 인터페이스를 정의한다. | SSDD | SFR(체계 기능 검토) |
| SW 요구사항 분석 | CSCI를 식별하고 기능·품질 요구사항과 제약 조건을 명세화한다. | SRS | SSR(소프트웨어 요구사항 검토) |
| SW 구조 및 상세설계 | 구성요소의 구조, 인터페이스, 단위별 설계를 구체화한다. | SDD | PDR(기본설계 검토), CDR(상세설계 검토) |
| SW 구현 및 시험 | 설계를 코드로 구현하고 단위·통합 수준에서 시험한다. | 소스코드, STP, STD, STR | 사업별 검토 절차 |
| 체계 통합 및 시험 | 구성품을 통합하고 체계 요구사항 충족 여부를 확인한다. | 체계 시험 관련 산출물 | TRR(시험준비상태 검토) 등 |

표는 강의에서 다룬 개발 흐름의 예시다. 기술 검토 시점과 산출물 구성은 사업의 적용 규정과 개발 계획에 따라 달라진다. TRR은 해당 시험을 시작하기 전에 시험 대상, 환경, 절차의 준비 상태를 점검하는 검토다.

### 주요 문서 약어

| 구분 | 약어와 명칭 |
| --- | --- |
| 소요·운용 | ROC(작전운용성능), OCD(운용개념기술서), ORD(운용요구서) |
| 사업 | RFP(제안요청서), LOA(수락서, Letter of Offer and Acceptance) |
| 체계 | SSS(체계 요구사항 명세서), SSRS(체계·부체계 요구사항 명세서), SSDD(체계·부체계 설계기술서) |
| SW 요구사항·설계 | SRS(소프트웨어 요구사항 명세서), SDD(소프트웨어 설계기술서) |
| SW 시험·산출물 | STP(소프트웨어 시험계획서), STD(소프트웨어 시험절차서), STR(소프트웨어 시험결과서), SPS(소프트웨어 산출물 명세서) |

요구사항은 체계 명세에서 SW 명세로 구체화하고, 설계와 시험까지 추적할 수 있게 연결한다. 시험 문서에서는 계획(STP), 절차(STD), 결과(STR)를 이어서 확인한다.

## SW 요구사항 분석

- **개발 범위**부터 확인한다. 시스템 컨텍스트로 개발 대상의 경계와 외부 시스템과의 인터페이스를 표현한다. 새 요구사항이 들어오면 개발 범위에 포함되는지, 기존 요구사항과 설계·시험에 어떤 영향을 주는지 확인한다.
- **명확하고 검증 가능한 요구사항**을 작성한다. 요구사항 간 일관성, 누락 여부, 실현 가능성, 추적 가능성도 확인한다. 모호한 내용은 이해관계자와 논의한다. 결함을 후반부에 발견하면 명세, 설계, 코드, 시험을 함께 수정할 수 있다.
- 유스케이스로 외부 행위자와 시스템의 상호작용을 정리하고, 시각적 모델과 프로토타입으로 동작을 확인한다. 데이터 사전에는 데이터의 의미, 형식, 단위 등을 정의한다. 분석 결과는 SRS에 기록한다.

| 구분 | 핵심 질문 | 예시 |
| --- | --- | --- |
| 기능 요구사항 | 무엇을 해야 하는가? | 장치는 온도가 허용 상한을 넘으면 화면에 경보를 표시해야 한다. |
| 품질 요구사항 | 얼마나 잘 수행해야 하는가? | 장치는 허용 상한 초과를 감지한 뒤 2초 이내에 경보를 표시해야 한다. |
| 제약 조건 | 설계·구현에서 어떤 조건을 지켜야 하는가? | 펌웨어는 C 언어로 작성해야 한다. |

성능, 신뢰성, 가용성, 보안성, 유지보수성, 확장성, 사용성과 같은 품질 속성은 아키텍처 선택에 영향을 준다. 품질 요구사항은 측정 조건과 판정 기준을 함께 적는다. 위 예시의 수치는 설명용이다. [요구사항분석](./요구사항분석.md)

## 검증과 확인(V&V)

| 구분 | 핵심 질문 | 판단 기준 |
| --- | --- | --- |
| 검증(Verification) | 제품을 올바르게 만들었는가? | 개발 결과물이 명세와 설계를 충족하는가? |
| 확인(Validation) | 올바른 제품을 만들었는가? | 제품이 실제 사용자 요구와 의도한 사용 목적을 충족하는가? |

### SW 신뢰성 시험

사업에 적용되는 규정과 계약 요구사항에 따라 신뢰성 시험을 수행한다. 시험 기준을 충족한 뒤에도 시험에서 다루지 않은 입력이나 실행 환경에 결함이 남을 수 있다.

| 구분 | 수행 방식 | 확인 항목 |
| --- | --- | --- |
| 정적 시험 | 소프트웨어를 실행하지 않고 코드를 분석한다. | 코딩 규칙 준수, 잠재적 보안 취약점, 복잡도 등 코드 메트릭 |
| 동적 시험 | 소프트웨어를 실행해 동작을 확인한다. | 코드 커버리지(시험에서 실행된 코드의 범위), 실행 중 드러나는 결함 |

## SW 협력 및 형상관리

- **협력 관리**에서는 여러 개발 조직과 협력업체가 담당 범위, 인터페이스, 변경사항을 공유하고 검토 결과와 후속 조치를 기록한다.
- **형상관리**에서는 SW 구성요소와 산출물의 버전 및 변경 이력을 관리한다. 시험 결과에는 시험한 버전을 연결해 같은 대상을 다시 확인할 수 있게 한다.
- 강의에서 언급한 관리·협업 도구는 SLM과 Confluence다. 협력 관리와 형상관리의 세부 절차는 강의 메모의 보완 항목이다.
