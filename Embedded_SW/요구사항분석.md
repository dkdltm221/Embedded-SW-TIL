# 요구사항분석

2026-11-24

## 요구사항의 정의

요구사항은 이해관계자의 목표를 달성하기 위해 필요한 기능이나 충족해야 하는 조건이다.

## 요구사항의 수준과 비즈니스 규칙

| 구분 | 핵심 질문 | 설명 | 온도 모니터링 장치 예시 |
| --- | --- | --- | --- |
| 비즈니스 요구사항 | 조직은 왜 이 시스템을 만드는가? | 시스템을 도입하는 이유와 조직이 얻고자 하는 효과를 정의한다. 사용자 요구사항과 기능 요구사항의 방향을 제시한다. | 보관 설비의 온도 이상을 조기에 발견해 제품 손실을 줄인다. |
| 사용자 요구사항 | 사용자가 제품으로 어떤 일을 할 수 있어야 하는가? | 사용자가 달성할 목표, 수행할 작업, 사용에 중요한 제품 특성을 설명한다. | 작업자는 현재 온도를 확인하고 온도가 허용 상한을 넘으면 알림을 받을 수 있어야 한다. |
| 시스템 요구사항 | 시스템 전체가 무엇을 충족해야 하는가? | 시스템 전체의 기능과 성능, 제약 조건을 명시한다. 하드웨어와 소프트웨어의 동작 및 하위 시스템 간 인터페이스도 포함할 수 있다. | 장치는 센서에서 1초마다 온도를 읽고, 상한 초과를 감지하면 2초 이내에 경보를 표시해야 한다. |
| 비즈니스 규칙 | 업무에 어떤 기준을 적용하는가? | 조직 정책, 법규, 산업 표준, 계산 기준 등 업무에 적용되는 규칙이다. 소프트웨어와 별개로 존재하며 시스템 요구사항의 근거가 될 수 있다. | 사내 보관 기준에서 허용 온도의 상한을 30 °C로 정한다. |

## 요구사항의 유형

| 유형 | 핵심 질문 | 설명 | 온도 모니터링 장치 예시 |
| --- | --- | --- | --- |
| 기능적 요구사항 | 시스템은 무엇을 해야 하는가? | 특정 입력이나 조건에서 소프트웨어가 어떤 동작을 해야 하는지 명시한다. | 온도가 허용 상한을 넘으면 화면에 경보를 표시해야 한다. |
| 품질 속성 (비기능적 요구사항) | 시스템은 얼마나 잘 동작해야 하는가? | 성능, 신뢰성, 사용성 등 시스템이 충족해야 하는 품질 수준을 명시한다. | 온도 상한 초과를 감지한 뒤 2초 이내에 경보를 표시해야 한다. |
| 인터페이스 요구사항 | 시스템은 외부와 어떻게 상호작용하는가? | 사용자, 외부 장치, 다른 시스템과 정보를 주고받는 방식과 데이터 형식 등을 명시한다. | 장치는 외부 관제 시스템에 현재 온도를 Modbus RTU로 전송해야 한다. |
| 제약 조건 | 설계와 구현에서 어떤 선택이 제한되는가? | 개발자가 지켜야 하는 언어, 플랫폼, 표준 등 설계·구현상의 제한을 명시한다. | 펌웨어는 C 언어로 작성해야 한다. |

## 국방 체계개발에서의 요구사항

### 개발 생명주기

제안서 → 계약 → 시스템 분석 → **요구사항 분석** → 기본설계 → 상세설계 → 구현 → 단위시험 → 통합시험 → 시험평가 → 납품

### 문서 흐름

| 구간 | 문서 흐름 |
| --- | --- |
| 소요·운용 및 체계 | ROC → OCD → ORD → RFP/LOA → SSS/SSRS → SSDD |
| 소프트웨어 요구사항·설계 | SRS(소프트웨어 요구사항 명세서) → SDD(소프트웨어 설계기술서) |
| 소프트웨어 시험·산출물 | STP(통합시험계획서) → STD(통합시험절차서) → STR(통합시험결과서) → SPS(산출물명세서) |

문서 순서는 기존 메모를 따랐으며, 소프트웨어 문서 명칭은 방위사업청 자료를 참고했다. [방위사업청 소프트웨어 기술문서 자료](https://dapa.go.kr/dapa/doc/selectDocList.do?bbsSeq=462&ctgrySeq=214&menuSeq=3042)

| 개발 단계 | 관련 산출물 | 주요 검토회의 |
| --- | --- | --- |

| 체계 구조 설계 | SSDD | SFR(체계 기능 검토) |

| 소프트웨어 구조 설계 | SDD | CDR(상세설계 검토) |
| 소프트웨어 구현 및 통합시험 | STD, STR | |

## 요구공학의 주요 활동

| 활동 | 하는 일 |
| --- | --- |
| 도출 | 이해관계자의 목표, 업무 규칙, 사용 환경 등을 살펴 필요한 요구사항을 찾아낸다. |
| 분석 | 도출한 요구사항의 의미와 범위를 명확히 하고, 큰 요구사항을 구체적인 하위 요구사항으로 나눈다. |
| 명세 | 정리된 요구사항을 SRS에 기록한다. 필요한 경우 표나 다이어그램을 사용한다. |
| 검증 | SRS를 검토해 개발에 필요한 요구사항이 명확하고 빠짐없이 작성됐는지 확인하고, 요구사항별 시험 기준을 마련한다. |

도출 ↔ 분석 ↔ 명세 ↔ 검증은 반복할 수 있다. 분석 중 뜻이 모호하면 도출 단계로 돌아가 명확히 한다. 명세 중 요구사항 사이에 빈틈이 드러나면 분석을 통해 보완한다. 검증에서 문제를 발견하면 명세를 다시 작성하고, 필요에 따라 분석으로 돌아가 재평가하거나 도출로 돌아가 확인·수정한다.

## 요구사항 도출 및 분석

### 도출 기법

| 구분 | 기법 | 활용 방법 |
| --- | --- | --- |
| 상호작용 | 인터뷰 | 이해관계자에게 업무 목표와 어려움을 질문하고 답변을 바탕으로 추가 질문을 한다. 개별 인터뷰는 참여자 전원의 공통 일정을 맞출 필요가 없다. |
| 상호작용 | 워크숍 | 여러 이해관계자가 함께 요구사항을 도출하고, 서로 다른 관점을 확인하거나 조율한다. |
| 상호작용 | 관찰 | 실제 업무 환경에서 사용자의 작업 흐름을 살핀다. 업무에 개입하지 않고 지켜보거나, 작업 중 질문하며 의도를 확인할 수 있다. 관찰 시간과 대상을 미리 정한다. |
| 상호작용 | 설문 | 규모가 큰 사용자 집단에 같은 질문을 보내 여러 사용자의 요구와 응답 경향을 파악한다. |
| 독립 활동 | 시스템 인터페이스 분석 | 컨텍스트 다이어그램으로 시스템 경계와 외부 시스템을 식별한다. 외부 시스템이 제공하는 기능, 교환하는 데이터와 서비스, 데이터 규칙과 유효성 검사 기준에서 요구사항을 도출한다. |
| 독립 활동 | 사용자 인터페이스 분석 | 기존 시스템이나 유사 제품의 화면과 스크린샷을 살펴 사용자가 자주 수행하는 작업 단계를 파악한다. 이를 바탕으로 사용자 요구사항, 기능적 요구사항, 유스케이스 초안을 작성한다. |
| 독립 활동 | 문서 분석 | 기존 요구사항 명세서와 사용설명서에서 유지하거나 제거할 기능을 찾는다. 사내 규정과 산업 표준에서 지켜야 할 조건을 확인한다. |

상호작용 기법과 기존 자료를 검토하는 기법은 함께 사용할 수 있다. [IREB 요구사항 도출 핸드북](https://cockpit.ireb.org/media/pages/downloads/cpre-requirements-elicitation-handbook/adc3d55045-1733311667/advanced_level_elicitation_handbook_en_v2.1.pdf)

### 도출 결과와 확인할 사항

- **도출 결과**에는 비즈니스·사용자 요구사항, 비즈니스 규칙, 기능적 요구사항, 품질 속성, 외부 인터페이스 요구사항, 제약 조건, 데이터 요구사항 등이 포함된다.
- **해결책 아이디어**가 나오면 후보로 기록하고, 어떤 사용자 목표나 요구사항을 충족하는지 확인한다.
- **도출 과정**에서는 영향을 받는 이해관계자 집단이 고르게 참여하는지, 시스템 범위가 적절히 정의됐는지, 제안된 설계 방식이 필수 제약인지 선택 가능한 해결책인지 확인한다.

### 요구사항 분석 방법

| 방법 | 확인할 내용 |
| --- | --- |
| 타당성 분석 | 허용 가능한 비용과 성능 수준에서 구현할 수 있는지 평가한다. 요구사항 간 의존성, 충돌, 기술적 제약을 확인한다. |
| 우선순위 결정 | 비즈니스 가치, 긴급성, 의존성 등을 고려해 구현 순서를 정한다. |
| 데이터 사전 작성 | 데이터 항목별로 이름, 의미, 형식, 단위, 허용 범위를 정의한다. |
| 요구사항 모델링 | 업무 흐름, 시스템 상태, 데이터 관계 등을 모델로 표현해 누락이나 모순을 찾는다. |
| 외부 인터페이스 분석 | 외부 시스템과 주고받을 데이터와 서비스의 형식, 방향, 오류 처리 조건 등을 구체화한다. |
| 하위 시스템에 요구사항 할당 | 각 요구사항을 충족할 책임이 어느 하위 시스템에 있는지 정한다. |

| --- | --- | --- |

### 유스케이스로 사용자 요구사항 분석하기

유스케이스는 일차 액터가 목표를 달성하기 위해 시스템과 상호작용하는 과정을 설명한다. **시스템 범위, 일차 액터, 목표 수준**을 먼저 정하고, 이해관계자의 관심사, 시나리오, 성공 기준, 실패했을 때도 지켜야 할 최소 조건을 기록한다.

| 항목 | 온도 이상 확인 예시 |
| --- | --- |
| 범위·일차 액터·목표 | 작업자가 온도 모니터링 장치의 경보에 대응해 현재 온도가 상한을 넘는지 확인한다. |
| 기본 시나리오 | 장치가 경보를 표시하면 작업자가 경보 화면을 열어 현재 온도와 허용 상한을 확인한다. |
| 성공 기준 | 작업자가 온도와 상한을 비교해 온도 이상 여부를 판단할 수 있다. |
| 예외 시나리오와 최소 조건 | 센서 값을 읽을 수 없으면 장치는 현재 온도를 측정할 수 없다는 상태를 표시한다. |

### 품질 요구사항 분석하기

서비스 연속성과 같은 비즈니스 목표에서 필요한 시스템 품질을 도출하고, 그 품질을 달성할 수 있도록 아키텍처를 설계한다. 품질 요구사항에는 적용 조건과 측정 가능한 기준을 함께 적는다. [CMU 소프트웨어공학연구소의 품질 속성과 아키텍처 자료](https://sei.cmu.edu/library/quality-attributes-and-service-oriented-architectures/)

**가용성**은 시스템이 필요한 시점에 서비스를 제공할 수 있는 정도다. 고장과 복구 시간으로 가용성을 추정할 때는 `MTBF / (MTBF + MTTR) × 100%`를 사용한다. **MTBF**는 고장 사이의 평균 가동 시간이고, **MTTR**은 고장 후 서비스가 복구되기까지 걸리는 평균 시간이다. [IBM 가용성 지표 설명](https://www.ibm.com/docs/en/itcam-transactions/7.4.0?topic=reports-viewing-trends-birt)

## 요구사항 명세화

### 소프트웨어 요구사항 명세서(SRS)

SRS는 소프트웨어에 필요한 기능, 성능, 외부 인터페이스, 설계 제약 등을 기록한 문서다. 합의된 필수 요구사항은 구현과 시험의 기준으로 사용한다. [ISO/IEC/IEEE 29148의 SRS 정의](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso-iec-ieee%3A29148%3Aed-2%3Av1%3Aen)

| 작성 수준 | 고려할 상황 |
| --- | --- |
| 간략한 명세 | 다양한 고객이 사용하는 다목적 제품이거나, 재사용 가능한 구성요소와 패키지 솔루션을 활용하는 경우에는 핵심 기능과 제약 중심으로 작성할 수 있다. |
| 상세한 명세 | 외주 개발, 분산된 프로젝트 팀, 요구사항을 바탕으로 시험을 설계하는 프로젝트에서는 구현 조건과 합격 기준을 구체적으로 작성한다. |

### 명세서 작성 지침

- **관점과 표현**을 통일한다. 시스템 동작을 기술할 때는 `장치는 … 해야 한다`처럼 작성하고, 의무 표현은 `해야 한다`로 통일한다.
- **하나의 항목에 하나의 의무**를 담는다. 짧은 능동형 문장으로 쓰고, 행위자와 동작이 시작되는 이벤트나 조건을 명시한다.
- **검증할 수 있게** 작성한다. `빠르게` 같은 모호한 표현은 시간이나 수치로 구체화하고, 필요한 입력·조건·단위·예외를 빠뜨리지 않는다.
- **내용에 맞는 형식**을 사용한다. 조건 조합은 표, 업무나 상태 변화는 분석 모델, 계산 규칙은 공식으로 표현할 수 있다.
- **우선순위**를 요구사항별로 정해 명세서에 기록한다.

> 장치는 측정 온도가 30 °C를 초과한 것을 감지한 뒤 2초 이내에 화면에 경보를 표시해야 한다.

## 요구사항 검증

- **검증(Verification)**은 시스템이 명세된 요구사항을 충족하는지 확인하는 활동이다.
- **확인(Validation)**은 시스템이 의도한 용도와 이해관계자의 요구를 충족하는지 확인하는 활동이다.

검사는 검증에 사용할 수 있는 방법 중 하나다.

## 요구사항 관리

요구사항 관리는 프로젝트 전반에 걸쳐 요구사항의 무결성, 정확성, 최신성을 유지하는 활동이다. 요구사항이 바뀌면 변경 내용과 이력을 관리한다.

## 대공유도탄 모의시스템 실습

시스템은 운용통제기, 공중위협 모의기, 대공유도탄 모의기로 구성된다. 각 구성 요소의 요구사항을 분석하고 설계, 구현, 시험을 수행한다.

### 구성 요소별 요구사항

#### 운용통제기

- 공중위협 시나리오의 초기 위치와 목적 위치를 설정한다.
- 유도탄 발사 지점을 설정한다.
- 시나리오 배포, 모의 시작·중지, 모의 발사를 제어한다.
- 운용 상태, 모의기 상태, 제어 상태를 표시한다.
- 모의 중 공중위협과 대공유도탄의 위치를 표시한다.
- 시작, 중지, 탐지, 발사, 요격, 요격 실패 등의 모의 이벤트를 표시한다.

#### 공중위협 모의기

- 설정된 초기 위치와 목적 위치에 따라 공중위협의 이동을 모의한다.
- 요격 이벤트를 처리한다.

#### 대공유도탄 모의기

- 공중위협 위치에 대한 대공유도탄의 추적과 요격을 모의한다.
- 발사 및 요격 이벤트를 처리한다.
